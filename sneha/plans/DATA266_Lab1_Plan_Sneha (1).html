00How to use this document

Read once, then work top to bottom.

This document is the complete build specification for Sneha's half of DATA 266 Lab 1. It is written so that a coding agent can execute it end to end without asking a follow up question: every path, every hyperparameter, every metric formula, and every output file is stated explicitly.

Order of operations

  1. Read section 1 and section 3 once. Those two sections constrain everything else.
  2. Run the repo bootstrap prompt below. It creates your folder tree and the config file.
  3. Work tasks in the order 1, 2, 3. Task 3 needs the most GPU time, so its data download and code should be ready before your first lab slot.
  4. After each task, run its acceptance check. Do not move on until it passes.

The logging contract

Every training entry point does the following, in this order, before it touches a model:

  1. Resolve the repo root by walking up from the script until it finds requirements.txt. Never use an absolute path.
  2. Load the config, hash it with SHA256, and print the hash as the first line of the log.
  3. Open reproducibility/raw_logs/sneha/<task>_<model>_<UTC timestamp>.log in append mode. If the file exists, abort rather than overwrite.
  4. Log the git commit SHA, the resolved device, the full config, and pip freeze output.
  5. Seed random, numpy, torch, and torch.cuda from config.seed, and set torch.backends.cudnn.deterministic = True.
  6. From then on, log one line per N steps with step, epoch, loss, learning rate, gradient norm, elapsed seconds, and peak memory. Never rewrite the file afterwards.

Manifest, one per task

At the end of every run, write reproducibility/manifests/sneha_task<n>.json containing: config hash, git SHA, seed, python and library versions, GPU name from torch.cuda.get_device_name(), wall clock duration, the checkpoint filename, and a metric_rows field that maps each checkpoint to the exact rows it produced in your metrics CSV. That mapping is what makes a number traceable at grading time.

Backup rule

GPU lab machines are wiped after your session. Copy checkpoints and logs off the machine at the end of every single session, not at the end of the project. A lost run cannot be recreated before the deadline.

04Task 1: GPT from scratch

TinyStories, character level, no prebuilt attention. 30 marks.

Build a decoder only GPT from scratch on TinyStories at the character level, and report on how it fails. Fifteen individual marks and fifteen team marks.

Architecture, exactly as specified

ComponentSpecificationWhy, and where it comes from
TokenisationCharacter level, built from your own training sliceBrief 1.1.1 and 1.1.3. Vocabulary is every unique character in your slice, mapped with your own char_to_idx and idx_to_char.
Token embeddingnn.Embedding(vocab, 256), learnedBrief 1.2.3
Positional embeddingnn.Embedding(128, 256), learned absoluteBrief 1.2.3 requires a learnable positional embedding, so fixed sinusoidal is not an option here
Blocks6 identical blocks, Post-normThis is the ordering in the original 2017 paper: sublayer first, then add the residual, then normalise. It is the historically faithful arrangement and it makes warmup a load bearing part of your recipe rather than a formality.
Attention8 heads, head dim 32, scaled dot product written by handScores are Q @ K.transpose(-2,-1) / sqrt(head_dim), masked with a registered lower triangular buffer, then softmax, then dropout, then @ V
Causal maskRegistered buffer torch.tril(torch.ones(T, T)), masked fill with -inf before softmaxBrief 1.2.2. Sliced to the current sequence length so shorter batches still work.
Feed forwardLinear 256 to 1024, ReLU, Linear back to 256, dropoutExpansion factor 4, as in the original paper. ReLU chosen to pair with post-norm.
Output headLayerNorm, then Linear 256 to vocabBrief 1.2.4
Weight tyingno weight tying, separate output projectionThe original Transformer used a separate output projection. Untied costs you one extra matrix, which you should report in your parameter count and comment on.
The one line defense of this lane

This is the decoder exactly as printed in Attention Is All You Need, six layers and eight heads, scaled down to fit a character level corpus. Nothing is invented. The payoff is that every question at the viva can be answered by pointing at the paper, and your warmup and schedule choices are not arbitrary defaults but load bearing parts of the original recipe that you can explain.

Known risk in this lane, and the fix

Post-norm needs its warmup. If your loss goes flat or diverges inside the first 300 steps, do not debug the architecture: raise warmup_steps to 800 and drop the peak learning rate to 1e-4, rerun, and keep both logs. Two logs showing the same model diverging then converging is genuinely good evidence for the stability metric the brief asks for, so treat a first failed run as data, not as lost time.

Data preparation

  1. Download the TinyStories corpus into task1_llm/data/. This folder is shared, download it once.
  2. Read the raw text, take a contiguous slice starting at an offset drawn from split_seed = 4242, and cut it into train_chars for training and the following val_chars for validation. The two slices must not overlap. The brief says each member creates their own split, which is why the seed is yours.
  3. Build the vocabulary from the training slice only. Any character seen only in validation maps to a single reserved unknown index.
  4. Encode to a single torch.long tensor. Sample training sequences as sliding windows of length block_size with the target being the input shifted one position left.
  5. Save char_to_idx and idx_to_char to outputs/vocab.json so generation is reproducible from the checkpoint alone.

05Task 2: Sentiment classification

Yelp polarity, three models, nothing pretrained. 30 marks.

A three model bake off on Yelp polarity with no pretrained anything. The dataset is 560,000 training reviews and 38,000 test reviews, balanced two class, where 1 and 2 stars are negative and 3 and 4 stars are positive. Fifteen individual marks and fifteen team marks.

Your three models

ModelConfigurationWhat this model is testing
Averaged embeddings
meanpool		Embedding 128, masked mean over non padding positions, two hidden layers of 256 with ReLU, dropout 0.3, single linear output. Adam 1e-3, batch 64.The floor. A deep averaging network with no word order at all. Iyyer et al. 2015. If a sequence model cannot beat this, that is the headline finding of the whole task.
BiGRU, max pooled
bigru		Embedding 128, one bidirectional GRU layer with hidden 128 per direction, max pooling over time, dropout 0.3. Packed sequences so padding is not fed through the recurrence.Whether word order buys anything over averaging. GRU rather than LSTM: fewer gates, fewer parameters, faster to train, and a cleaner comparison against the averaging baseline.
Character CNN
charcnn		Fixed 70 character alphabet, input length 1014, six 1D convolutions with 256 filters at kernel sizes 7, 7, 3, 3, 3, 3 with max pooling after layers 1, 2 and 6, then two fully connected layers of 512 with dropout 0.5.Whether a model that never sees a word can match one that does. This is the architecture from the paper that introduced this exact dataset, Zhang, Zhao and LeCun 2015, which makes it the single most citable model in the lab.
Why these three, as a set

A deliberately minimal baseline, then a recurrent model, then a model that throws away words entirely and reads characters. The spread is wide on purpose: if the word order model and the character model both land near the bag of words baseline, that is a real result about how easy this dataset is, and it is the most interesting thing anyone will write in the team analysis.

Data, shared with your partner

The split files are team owned and must exist before you train. Load the index arrays from task2_sentiment/data/splits/: 100,000 stratified training rows and 20,000 stratified validation rows drawn from the official training split with seed 42, and the full 38,000 row official test split. Do not resample them, do not reshuffle them, do not draw your own. Every accuracy number in the team comparison table and the paired McNemar test depends on both members scoring the identical test rows.

Preprocessing, yours alone, writes to your data_processed/

  1. Report the review length distribution, the class distribution, and the class balance, as three plots into outputs/. This is 10 marks of the task, do not skip the analysis.
  2. Drop or repair malformed rows: empty strings after cleaning, rows with a missing label, duplicated text. Log how many of each you removed.
  3. Lowercase, strip punctuation and special characters, unescape the doubled quotes and the literal backslash-n newlines that this dataset uses.
  4. Remove stopwords and apply lemmatisation, then state in results.md whether that helped or hurt, measured on the validation split. Both answers are acceptable, an unexamined choice is not.
  5. Tokenise and build a vocabulary capped at 30,000 types from the training split only, with reserved <pad> and <unk> indices. Pad or truncate to max_len = 256.
Preprocessing note for this lane

The character level model in this lane bypasses the word vocabulary entirely and uses its own fixed alphabet. Keep its preprocessing in a separate function so the two pipelines never contaminate each other.

Why this generator, and where it comes from

The U-Net generator ships in the official CycleGAN and pix2pix codebase as a first class option alongside the residual one, so it is fully paper backed and no part of it is improvised. Its skip connections carry high resolution detail straight from encoder to decoder, which tends to preserve the layout of the source image strongly. Watch for that in your own results and say so plainly in your analysis: strong content preservation and weaker stylisation is the expected signature of this generator, and noticing it in your own numbers, particularly in the content cosine and LPIPS columns, is exactly the kind of observation the analysis marks reward.

Discriminator, both of them

A 70 x 70 PatchGAN, identical for D_A and D_B, exactly as in the CycleGAN paper: C64 without normalisation, then C128, C256, C512, each being a 4 x 4 stride 2 convolution followed by InstanceNorm and LeakyReLU with slope 0.2, then a final 4 x 4 stride 1 convolution to a single channel. It outputs a 30 x 30 map of real or fake scores rather than one number, which is what makes it a patch discriminator. Do not apply a sigmoid, because the least squares loss expects raw scores.

Five marks that no amount of code can earn for you.

Five marks, scored on you alone, in a session the team attends together. Your leaderboard rank and your metric values are not what is being judged. Depth of understanding of your own implementation is.

What to have open on screen

  • Your three results.md files, one per task.
  • Your three metrics CSVs, and the loss curve images.
  • Your checkpoints, loadable, with a generation or inference cell already run once so it does not fail live.
  • Your failure_analysis.md files, since the examiners ask about failures more than about successes.

The five questions that come up in every one of these

QuestionWhat a good answer contains
Why this architecture?A constraint from the brief, a property of the data, and a number from your own run. Not a citation on its own.
How was this metric computed?The formula, the exact function you called, and what would change the value. If you cannot say what would move it, you do not understand it.
What went wrong?A specific failure you found, why you think it happened, and the one experiment that would test your explanation.
How does this differ from your teammate's model?One structural difference and one measured consequence of it. Look at the comparison table before the session.
What if you had changed X?A directional prediction with a reason. Being wrong with a reason scores better than refusing to guess.
How this is scored

The brief says it directly: a confident teammate cannot carry you, and the score reflects only on you. The corollary is that the last hour before the viva is better spent rereading your own logs than polishing a slide.

The forty minute rehearsal, worth doing once

  1. Open your Task 1 code and explain the causal mask out loud to an empty room. If you hesitate, reread that function.
  2. Pick one number from each metrics CSV and say what would make it go up.
  3. Pick your worst result across all three tasks and prepare the honest explanation. Examiners reward this and punish evasion.
  4. Read your partner's results.md files once so the comparison question does not surprise you.
